# Welcome Messages (`welcome_channel`)

> Module that posts one or more **Components V2** welcome messages in public
> channels when a member joins the server.
>
> Code: `modules/welcome_channel.py` · UI: `modules/configs/welcome_channel_config.py`
> · dispatch: `cogs/module_events.py` (`on_member_join`)
>
> Sibling module: [WELCOME_DM.md](WELCOME_DM.md) (`welcome_dm`) — same schema
> and same UI grammar, sent in private instead of a channel.

---

## 1. Overview

A guild can configure **up to 5 welcome messages** (`MAX_WELCOME_MESSAGES`) —
that cap is **per guild, all users combined**, not per user. Each message is
independent:

| Per-message setting | Meaning |
|---|---|
| `channel_id` | the text/announcement channel the message is posted in |
| `message` | the full text, with placeholders (see §3) |
| `accent_color` | the coloured bar on the left of the container (`null` = default) |
| `enabled` | pause a message without deleting it |

When a member joins, **every enabled message** is rendered and sent to its own
channel. Rendering is a `ui.LayoutView` holding a single `ui.Container`
(accent-coloured) with the formatted text — no `discord.Embed` anywhere.

Mentions are constrained to the joining member: `AllowedMentions(everyone=False,
roles=False, users=[member])`. A welcome message can never mass-ping.

---

## 2. Storage

Configuration is plain JSONB under `guilds.data.modules.welcome_channel` — the
standard module storage (see [MODULE_SYSTEM.md](MODULE_SYSTEM.md)). No dedicated
table.

```jsonc
{
  "version": 2,
  "messages": [
    {
      "id": "wm_3f9a1c72",              // stable id, "wm_" + 8 hex chars
      "channel_id": 123456789012345678,  // int (Discord snowflake), required
      "message": "Welcome {user} to **{server}**!\n-# They are the **{member_count}**th member",
      "accent_color": 5793266,           // int 0x000000–0xFFFFFF, or null = default
      "enabled": true,                   // bool
      "created_by": 987654321098765432,  // int, informational
      "created_at": "2026-08-07T12:34:56.789012+00:00"  // ISO 8601 UTC, informational
    }
  ]
}
```

### Field reference

| Field | Type | Required | Notes |
|---|---|---|---|
| `version` | `int` | yes | Schema version, currently `2`. Written on every save. |
| `messages` | `array` | yes | Max **5** entries. An empty array disables the module. |
| `messages[].id` | `string` | yes | Unique **within the guild**. Generated by the bot; the dashboard must generate ids of the same shape (`wm_` + 8 lowercase hex) for new entries and must **never** reuse an existing id. |
| `messages[].channel_id` | `int` | yes | Must be a text or announcement channel of the guild, where the bot can **View Channel** *and* **Send Messages**. |
| `messages[].message` | `string` | yes | Non-empty, **max 1500 characters** (`MAX_MESSAGE_LENGTH`). Markdown allowed, including headings (`#`, `##`, `###`) and subtext (`-#`). |
| `messages[].accent_color` | `int \| null` | no | `null` (or absent) falls back to `0x5865F2`. Stored as an integer, **not** a hex string. |
| `messages[].enabled` | `bool` | no | Defaults to `true`. `false` = configured but not sent. |
| `messages[].created_by` | `int \| null` | no | User id, informational only. |
| `messages[].created_at` | `string \| null` | no | ISO 8601 UTC, informational only. |

### Module `enabled` state

`enabled` is **computed, never stored**: the module is active as soon as at
least one entry has `enabled: true` *and* a `channel_id`. Do not write an
`enabled` key at the config root — it is ignored.

### v1 → v2 migration

The pre-rework schema (single channel + optional embed) is migrated **on read**
by `normalize_config()` in `modules/welcome_channel.py`:

| v1 key | becomes |
|---|---|
| `channel_id` | `messages[0].channel_id` |
| `message_template` | `messages[0].message` |
| `embed_color` | `messages[0].accent_color` |
| `mention_user`, `embed_*` | dropped |

The migration is pure — nothing is written back until the guild next saves from
`/config` (or the dashboard). A backend reading a raw config **must** apply the
same fallback, or treat a config without a `messages` key as v1.

## 3. Placeholders

Substitution is done with `str.replace`, **never** `str.format` — a stray `{`
in a user's message can never raise, and unknown `{tokens}` are left untouched.

| Placeholder | Replaced with |
|---|---|
| `{server}` | `guild.name` |
| `{user}` | `member.mention` (`<@id>`) |
| `{display_name}` | `member.display_name` (nickname / global name) |
| `{username}` | `member.name` (account name) |
| `{member_count}` | `guild.member_count` after the join |
| `{timestamp}` | join time, **unix seconds** — meant to be wrapped: `<t:{timestamp}:R>` |

Placeholders are advertised to the user inside the customization modal
(`_placeholder_help()`), one line per placeholder, localized.

### Default message

The pre-filled message is localized, under the i18n key
`modules.welcome_channel.default_message`. French reference:

```
Bienvenue à {user} sur **{server}** !
-# Il/elle est le **{member_count}**ᵉ membre
```

It is fetched **without** i18n kwargs so the literal braces survive. The
dashboard should offer the same default, in the user's language, when creating
a message.

## 4. Validation (server-side contract)

`WelcomeChannelModule.validate_config()` runs on every save and rejects the
whole config if any entry fails. The dashboard must enforce the same rules to
avoid a save that the bot refuses:

1. at most `5` entries;
2. no duplicate `id` within the guild;
3. `channel_id` present, resolvable in the guild, and a text channel;
4. bot has **View Channel** + **Send Messages** there;
5. `message` non-empty after trimming, `≤ 1500` characters;
6. `accent_color` either `null` or an `int` in `[0, 0xFFFFFF]`.

Errors are returned as localized strings under `modules.welcome_channel.errors.*`.

## 5. Dashboard / backend integration

- **Read**: `guilds.data.modules.welcome_channel`; apply the v1 fallback of §2.
- **Write**: replace the whole `welcome_channel` object (the bot always writes
  the full list — there is no per-entry patch endpoint). Keep `version: 2`.
- **Invalidate**: after writing, emit the existing `module_updated` Pub/Sub
  event so `ModuleManager` drops its cache and reloads from the DB — see
  [BACKEND-INTEGRATION.md](BACKEND-INTEGRATION.md). Without it the bot keeps
  serving the previously loaded config until the next restart.
- **Constants to mirror** (`modules/welcome_channel.py`):
  `MAX_WELCOME_MESSAGES = 5`, `MAX_MESSAGE_LENGTH = 1500`,
  `DEFAULT_ACCENT_COLOR = 0x5865F2`, `CONFIG_VERSION = 2`.
- **Colour format**: the UI shows `#RRGGBB`, the DB stores an `int`. Convert on
  both sides (`int(hex[1:], 16)` / `f"#{value:06X}"`).

## 6. Config UI

The `/config` panel follows the Social Notifications layout (list + add/manage)
rather than a single form, because a guild now has *n* messages:

```
Main panel ──► Add message ──► (channel + message customization) ──► confirm
          └──► Manage message ──► change channel / edit message / pause / remove
```

- Customization (text + accent colour + placeholder cheat-sheet) is a single
  **Modal V2** — see [MODALS_V2.md](MODALS_V2.md).
- Actions apply immediately (no Save/Cancel batching): each write goes through
  `module_manager.save_module_config`, so the config is revalidated and the
  module instance reloaded on every change.
- All three views are persistent (`moddy:welcomechan:<view>:<action>` custom_ids)
  and registered in `utils/persistent_views.py`. The add/manage wizard state is
  not persisted across a restart — same accepted loss as the Social
  Notifications add/manage views, see
  [PERSISTENT_VIEWS.md](PERSISTENT_VIEWS.md).
