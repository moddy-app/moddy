# 2026-10-27 — AltGuard contract update (consent 2026-10-27, inviter_id, new labels)

## What was done
- **Consent notice** replaced with the operator's 2026-10-27 notice (FR/EN verbatim,
  ES/PT/DE translated), split over two TextDisplays in the consent modal (the
  data table rendered as a bullet list). "Learn more" now links
  `https://verify.moddy.app/privacy`. `CONSENT_VERSION = "2026-10-27"`.
- **`inviter_id`** sent (as a string, omitted when unknown) with
  `POST /altguard/token`. New `services/altguard_invites.py` (`InviteTracker`)
  compares invite `uses` counters; baseline per AltGuard-enabled guild, kept
  current by `on_invite_create/delete`. The inviter is stored in the new
  `altguard_members.inviter_id` column at join and read at consent time.
- **Reason labels**: `modules.altguard.reasons.<code>` for all 24 codes (incl.
  new `connection_match`, `invited_by`, `vpn_detected`) rendered on the log card
  and in `/mod altguard refusal`; unknown codes shown raw.
- **VPN**: link card warns that verification is impossible behind a VPN/proxy.
  No code path treats a missing verdict as an error (none existed).

## Decisions
- Inviter resolution runs in a background task *after* the gate role is
  applied: it is a REST call serialized per guild, so awaiting it inline would
  delay gating during a raid.
- A cold cache attributes nobody (the spec's sample would attribute every used
  invite on the first join after a restart). Ambiguous joins → no inviter.
- `manage_guild` is NOT added to `REQUIRED_BOT_PERMISSIONS`: inviter attribution
  is optional and silently skipped without it.
- The inviter is persisted (not in memory) so it survives a restart between
  join and consent.

## Follow-ups
- Servers wanting inviter attribution must grant Moddy *Manage Server*; no UI
  hints at it yet.
- Disabling the VPN block per server needs a new AltGuard endpoint (not exposed).
