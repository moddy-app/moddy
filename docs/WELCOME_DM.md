# Welcome DM (`welcome_dm`)

> Module that sends one or more **Components V2** welcome messages in private to
> a member who joins the server.
>
> Code: `modules/welcome_dm.py` · UI: `modules/configs/welcome_dm_config.py`
> · dispatch: `cogs/module_events.py` (`on_member_join`)
>
> Sibling module: [WELCOME_MESSAGES.md](WELCOME_MESSAGES.md) (`welcome_channel`)
> — same schema, same UI grammar, but posted in a public channel.

---

## 1. Overview

A guild can configure **up to 3 welcome DMs** (`MAX_WELCOME_DMS`) — that cap is
**per guild, all users combined**, not per user. It is deliberately lower than
the channel module's `5`: every entry is one more private message pushed at the
same person the second they join. Each message is independent:

| Per-message setting | Meaning |
|---|---|
| `message` | the full text, with placeholders (see §3) |
| `accent_color` | the coloured bar on the left of the container (`null` = default) |
| `enabled` | pause a message without deleting it |

When a member joins, **every enabled message** is rendered and sent to them, in
configuration order. Rendering is a `ui.LayoutView` holding a single
`ui.Container` (accent-coloured) with the formatted text — no `discord.Embed`
anywhere.

A member with DMs closed makes the first send come back `forbidden`; the module
stops there instead of retrying the remaining entries (see §7 — delivery goes
through the notification system, which does not raise on a closed DM).

Mentions are constrained to the joining member: `AllowedMentions(everyone=False,
roles=False, users=[member])`. A DM cannot mass-ping in the first place, but the
constraint keeps the two welcome modules identical.

## 2. Storage

Configuration is plain JSONB under `guilds.data.modules.welcome_dm` — the
standard module storage (see [MODULE_SYSTEM.md](MODULE_SYSTEM.md)). No dedicated
table.

```jsonc
{
  "version": 2,
  "messages": [
    {
      "id": "wdm_3f9a1c72",              // stable id, "wdm_" + 8 hex chars
      "message": "Welcome to **{server}**, {display_name}!",
      "accent_color": 5793266,           // int 0x000000–0xFFFFFF, or null = default
      "enabled": true,                   // bool
      "created_by": 987654321098765432,  // int, informational
      "created_at": "2026-08-21T12:34:56.789012+00:00"  // ISO 8601 UTC, informational
    }
  ]
}
```

### Field reference

| Field | Type | Required | Notes |
|---|---|---|---|
| `version` | `int` | yes | Schema version, currently `2`. Written on every save. |
| `messages` | `array` | yes | Max **3** entries. An empty array disables the module. |
| `messages[].id` | `string` | yes | Unique **within the guild**. Generated by the bot; the dashboard must generate ids of the same shape (`wdm_` + 8 lowercase hex) for new entries and must **never** reuse an existing id. |
| `messages[].message` | `string` | yes | Non-empty, **max 1500 characters** (`MAX_MESSAGE_LENGTH`). Markdown allowed, including headings (`#`, `##`, `###`) and subtext (`-#`). |
| `messages[].accent_color` | `int \| null` | no | `null` (or absent) falls back to `0x5865F2`. Stored as an integer, **not** a hex string. |
| `messages[].enabled` | `bool` | no | Defaults to `true`. `false` = configured but not sent. |
| `messages[].created_by` | `int \| null` | no | User id, informational only. |
| `messages[].created_at` | `string \| null` | no | ISO 8601 UTC, informational only. |

There is **no channel** on a DM entry — that is the only structural difference
with `welcome_channel`.

### Module `enabled` state

`enabled` is **computed, never stored**: the module is active as soon as at
least one entry has `enabled: true`. Do not write an `enabled` key at the config
root — it is ignored.

### v1 → v2 migration

The pre-rework schema (single `message_template` + optional embed) is migrated
**on read** by `normalize_config()` in `modules/welcome_dm.py`:

| v1 key | becomes |
|---|---|
| `embed_title` (only when `embed_enabled`) | a `### ` heading at the top of `messages[0].message` |
| `message_template` | the body of `messages[0].message` |
| `embed_description` (only when `embed_enabled`, when it differs from the template) | appended to `messages[0].message` |
| `embed_color` (only when `embed_enabled`) | `messages[0].accent_color` |
| `embed_footer`, `embed_image_url`, `embed_thumbnail_enabled`, `embed_author_enabled` | dropped |

The composed text is truncated to `MAX_MESSAGE_LENGTH`. A v1 config that ends up
with no text at all migrates to an empty `messages` list (module off).

The migration is pure — nothing is written back until the guild next saves from
`/config` (or the dashboard). A backend reading a raw config **must** apply the
same fallback, or treat a config without a `messages` key as v1.

## 3. Placeholders

Substitution is done with `str.replace`, **never** `str.format` — a stray `{`
in a user's message can never raise, and unknown `{tokens}` are left untouched.

| Placeholder | Replaced with |
|---|---|
| `{server}` | `guild.name` |
| `{user}` | `member.mention` (`<@id>`) |
| `{display_name}` | `member.display_name` (nickname / global name) |
| `{username}` | `member.name` (account name) |
| `{member_count}` | `guild.member_count` after the join |
| `{timestamp}` | join time, **unix seconds** — meant to be wrapped: `<t:{timestamp}:R>` |

Placeholders are advertised to the user inside the customization modal
(`_placeholder_help()`), one line per placeholder, localized.

### Default message

The pre-filled message is localized, under the i18n key
`modules.welcome_dm.default_message`. French reference:

```
Bienvenue sur **{server}**, {display_name} !
-# Tu es le **{member_count}**ᵉ membre à nous rejoindre.
```

It is fetched **without** i18n kwargs so the literal braces survive. The
dashboard should offer the same default, in the user's language, when creating
a message.

## 4. Validation (server-side contract)

`WelcomeDmModule.validate_config()` runs on every save and rejects the whole
config if any entry fails. The dashboard must enforce the same rules to avoid a
save that the bot refuses:

1. at most `3` entries;
2. no duplicate `id` within the guild;
3. `message` non-empty after trimming, `≤ 1500` characters;
4. `accent_color` either `null` or an `int` in `[0, 0xFFFFFF]` (a non-int value
   is normalized to `null` on read rather than rejected).

Errors are returned as localized strings under `modules.welcome_dm.errors.*`.

## 5. Dashboard / backend integration

- **Read**: `guilds.data.modules.welcome_dm`; apply the v1 fallback of §2.
- **Write**: replace the whole `welcome_dm` object (the bot always writes the
  full list — there is no per-entry patch endpoint). Keep `version: 2`.
- **Invalidate**: after writing, emit the existing `module_updated` Pub/Sub
  event so `ModuleManager` drops its cache and reloads from the DB — see
  [BACKEND-INTEGRATION.md](BACKEND-INTEGRATION.md). Without it the bot keeps
  serving the previously loaded config until the next restart.
- **Constants to mirror** (`modules/welcome_dm.py`): `MAX_WELCOME_DMS = 3`,
  `MAX_MESSAGE_LENGTH = 1500`, `DEFAULT_ACCENT_COLOR = 0x5865F2`,
  `CONFIG_VERSION = 2`.
- **Colour format**: the UI shows `#RRGGBB`, the DB stores an `int`. Convert on
  both sides (`int(hex[1:], 16)` / `f"#{value:06X}"`).

## 6. Config UI

The `/config` panel follows the Welcome Channel layout (list + add/manage):

```
Main panel ──► Add message (Modal V2) ──► saved
          └──► Manage message ──► edit message / pause / remove
```

- There is nothing to pick before writing a DM (no channel), so **"Add" is the
  customization modal itself** — the modal submits straight into the message
  list. That is the one deliberate difference with `welcome_channel`, which
  needs an intermediate view to hold the channel picker.
- Customization (text + accent colour + placeholder cheat-sheet) is a single
  **Modal V2** — see [MODALS_V2.md](MODALS_V2.md).
- Entries have no channel to name them, so the list numbers them
  (`Message 1`, `Message 2`, …) in configuration order and shows a one-line
  preview of the stored text.
- Actions apply immediately (no Save/Cancel batching): each write goes through
  `module_manager.save_module_config`, so the config is revalidated and the
  module instance reloaded on every change.
- Both views are persistent (`moddy:welcomedm:<view>:<action>` custom_ids) and
  registered in `utils/persistent_views.py`. The manage view's current entry is
  not persisted across a restart — same accepted loss as
  `ManageWelcomeMessageView`, see [PERSISTENT_VIEWS.md](PERSISTENT_VIEWS.md).

## 7. Delivery: through the notification system

Welcome DMs are not sent with `member.send(...)`. They go through
`bot.notifications.send_dm()` — see [NOTIFICATIONS.md](NOTIFICATIONS.md) — which
changes three things:

- **Every DM is recorded.** One `notifications` row per member, carrying its
  uuid (what staff look up with `/mod notif`), the delivery result, and the
  `variables` that were substituted (`message_variables()`), so the exact
  wording sent to a given member can be rebuilt later. The body itself is
  stored **as a template**, placeholders unresolved (`welcome_content()` keeps
  `{server}` / `{user}` in the text), so all the members of one server share a
  single stored content row.
- **It is attributed to the server.** The DM ends with one greyed line —
  `-# Sent by [**Server**](https://discord.com/channels/<id>) (`<id>`)`, plus
  the verification check when the server carries one — so the recipient can
  always tell which server DMed them.
- **It is marked reportable.** The source is `NotificationSource.guild(guild.id)`,
  whose default author is `ContentAuthor.GUILD`: the text is the server's own
  words, which is exactly what can be abused. That flag is what an abuse report
  against a welcome DM will be checked against.

`send_dm()` returns a `DeliveryResult` instead of raising: `result.forbidden`
means the member's DMs are closed (the module stops there), `result.delivered`
that the message went out, and `result.notification_id` is what the module logs.

The rendered container is unchanged — the module still builds its own
Components V2 view holding only the guild's text — and is passed as `view=`;
the attribution line is appended inside its container. The uniform `content` is
still required: it is what the dashboard and the mail pipeline render, and what
a staff reviewer sees when handling a report.
