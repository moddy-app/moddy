# Welcome DM — backend / dashboard implementation guide

> Everything the backend (and the dashboard behind it) needs to read, write and
> invalidate the `welcome_dm` module configuration.
>
> Module reference (schema rationale, UI, rendering): [WELCOME_DM.md](WELCOME_DM.md)
> · Redis contract: [REDIS_COMMUNICATION.md](REDIS_COMMUNICATION.md)
> · Generic module storage: [MODULE_SYSTEM.md](MODULE_SYSTEM.md)

---

## 1. TL;DR

| Question | Answer |
|---|---|
| Where is it stored? | `guilds.data -> 'modules' -> 'welcome_dm'` (JSONB), no dedicated table |
| Shape | `{ "version": 2, "messages": [ … ] }`, max **3** entries |
| Write granularity | **Replace the whole object.** There is no per-entry patch |
| Who validates? | Both sides. The bot re-validates on its own writes; the backend must mirror §4 or the dashboard will let users save something the bot would refuse |
| After writing? | Publish `module_updated` on `moddy:bot`, otherwise the bot serves the previously loaded config until the next restart |
| Disable the module | Set `messages: []` (or every entry `enabled: false`). There is **no** root `enabled` key |

## 2. Storage & SQL

The `guilds` table has a `data` JSONB column; every module owns one key under
`data.modules`. The bot writes through
`ModdyDatabase.update_guild_data(guild_id, "modules.welcome_dm", config)`, which
reads `data`, sets the nested path in Python and writes the whole `data` back —
so from the backend's side, any equivalent JSONB write is fine.

### Read

```sql
SELECT data #> '{modules,welcome_dm}' AS config
FROM guilds
WHERE guild_id = $1;
```

`NULL` / `{}` / a missing `messages` key all mean **not configured (v2)** — but
see §5: a config without `messages` may be a **v1** config that still has to be
migrated on read.

### Write (upsert, full replace)

```sql
INSERT INTO guilds (guild_id, data, attributes, created_at, updated_at)
VALUES ($1, jsonb_build_object('modules', jsonb_build_object('welcome_dm', $2::jsonb)),
        '{}'::jsonb, NOW(), NOW())
ON CONFLICT (guild_id) DO UPDATE
SET data = jsonb_set(
        COALESCE(guilds.data, '{}'::jsonb),
        '{modules,welcome_dm}',
        $2::jsonb,
        true                      -- create_missing
    ),
    updated_at = NOW();
```

`$2` is the **complete** config object, `version` included. Never merge
key-by-key: a removed message must disappear from the array, and a partial merge
would resurrect it.

### Delete / reset

The bot's "delete config" path writes an empty object:

```sql
UPDATE guilds
SET data = jsonb_set(data, '{modules,welcome_dm}', '{}'::jsonb, true),
    updated_at = NOW()
WHERE guild_id = $1;
```

`{}` reads back as "not configured" (`normalize_config()` returns an empty
`messages` list), which is also how the module ends up disabled.

## 3. Schema

```jsonc
{
  "version": 2,                          // int, always write 2
  "messages": [                          // max 3 entries
    {
      "id": "wdm_3f9a1c72",              // string, "wdm_" + 8 lowercase hex
      "message": "Welcome to **{server}**, {display_name}!",
      "accent_color": 5793266,           // int 0x000000–0xFFFFFF | null
      "enabled": true,                   // bool, default true
      "created_by": 987654321098765432,  // int | null, informational
      "created_at": "2026-08-21T12:34:56.789012+00:00"  // ISO 8601 UTC | null
    }
  ]
}
```

TypeScript, if that helps:

```ts
type WelcomeDmConfig = {
  version: 2;
  messages: WelcomeDmMessage[];          // length <= 3
};

type WelcomeDmMessage = {
  id: string;                            // /^wdm_[0-9a-f]{8}$/
  message: string;                       // 1..1500 chars, trimmed
  accent_color: number | null;           // 0..0xFFFFFF
  enabled: boolean;
  created_by?: number | null;
  created_at?: string | null;            // ISO 8601 UTC
};
```

Notes that bite:

- **`id` is generated by the writer.** The bot uses `secrets.token_hex(4)`; the
  dashboard must generate ids of the same shape for new entries and must
  **never** reuse or renumber an existing one — the bot matches entries by `id`
  when editing/pausing/removing from `/config`.
- **`accent_color` is an `int`, not a hex string.** The UI shows `#RRGGBB`:
  convert on both sides (`parseInt(hex.slice(1), 16)` /
  `'#' + v.toString(16).toUpperCase().padStart(6, '0')`). `null` means "use the
  default", `0x5865F2`.
- **A non-int `accent_color` is not rejected**, it is normalized to `null` on
  read. Don't rely on that — validate before writing.
- `created_by` / `created_at` are informational. The bot never reads them back
  for logic; keep them if present, fill them for new entries.
- **There is no `channel_id`.** That is the only structural difference with
  `welcome_channel` ([WELCOME_MESSAGES.md](WELCOME_MESSAGES.md)), whose entries
  are otherwise identical.

### Derived state

`enabled` at the module level is **computed, never stored**: the module is
active as soon as at least one entry has `enabled: true`. If the dashboard shows
a module on/off switch, map it to the entries (pause them all / resume them),
and do not invent a root `enabled` key — the bot ignores it.

## 4. Validation rules to mirror

`WelcomeDmModule.validate_config()` runs on every bot-side save and rejects the
**whole** config if any entry fails:

| # | Rule | Bot error key (`modules.welcome_dm.errors.*`) |
|---|---|---|
| 1 | at most **3** entries | `too_many` |
| 2 | no duplicate `id` inside the guild | `duplicate_id` |
| 3 | `message` non-empty after trimming | `empty_message` |
| 4 | `message` ≤ **1500** characters | `message_too_long` |
| 5 | `accent_color` is `null` or an `int` in `[0, 0xFFFFFF]` | `invalid_color` |

Nothing else is enforced: markdown, headings (`#`, `##`, `###`), subtext (`-#`)
and unknown `{tokens}` are all allowed inside `message`.

Two rules the bot enforces *outside* `validate_config()` and that a dashboard
save also hits, via `module_manager.save_module_config`:

- the guild (or the acting user) must not be under a **global "limited"
  sanction** if the module is not configured yet — see
  [GLOBAL_SANCTIONS.md](GLOBAL_SANCTIONS.md);
- unknown module ids are refused.

## 5. v1 → v2 migration (read path)

A guild that never re-saved since the rework still has the **v1** object:

```jsonc
{
  "message_template": "Bienvenue sur le serveur {server} !",
  "embed_enabled": true,
  "embed_title": "Bienvenue !",
  "embed_description": "Lis les règles.",
  "embed_color": 5793266,
  "embed_footer": null,
  "embed_image_url": null,
  "embed_thumbnail_enabled": true,
  "embed_author_enabled": false
}
```

The bot migrates it **on read** (`normalize_config()`, pure — nothing is written
back until the next save). Any backend that reads the raw config must apply the
same fallback, or treat "no `messages` key" as v1:

| v1 key | becomes |
|---|---|
| `embed_title` (only if `embed_enabled`) | a `### ` heading on the first line of `messages[0].message` |
| `message_template` | the body of `messages[0].message` |
| `embed_description` (only if `embed_enabled`, and if different from the template) | appended after the body |
| `embed_color` (only if `embed_enabled`) | `messages[0].accent_color` |
| `embed_footer`, `embed_image_url`, `embed_thumbnail_enabled`, `embed_author_enabled` | dropped |

The composed text is truncated to 1500 chars, gets a fresh `wdm_…` id and
`enabled: true`. If the composition is empty, the result is an empty `messages`
list (module off).

Reference implementation: `normalize_config()` in `modules/welcome_dm.py`.

**Recommended**: when the dashboard opens a v1 config, migrate it in memory,
show the v2 form, and write v2 back on the user's first save. Do not migrate
silently in a background job unless you also emit `module_updated`.

## 6. Placeholders (for the dashboard preview)

Substituted at send time with plain `str.replace` — never a format call — so an
unmatched `{` is harmless and unknown `{tokens}` stay visible in the DM.

| Placeholder | Replaced with |
|---|---|
| `{server}` | guild name |
| `{user}` | `<@user_id>` mention |
| `{display_name}` | nickname / global name |
| `{username}` | account name |
| `{member_count}` | member count after the join |
| `{timestamp}` | join time, **unix seconds** — meant to be used as `<t:{timestamp}:R>` |

A preview in the dashboard should do exactly the same substitution (literal
replace, unknown tokens untouched) to match what the member receives.

Default message for a new entry: i18n key `modules.welcome_dm.default_message`,
per locale (fr, en-US, es-ES, pt-BR, de). French reference:

```
Bienvenue sur **{server}**, {display_name} !
-# Tu es le **{member_count}**ᵉ membre à nous rejoindre.
```

## 7. Cache invalidation (mandatory)

`ModuleManager` keeps loaded module instances in memory. After **every** write,
publish on the `moddy:bot` Pub/Sub channel:

```jsonc
{
  "type": "module_updated",
  "guild_id": 123456789012345678,
  "module_id": "welcome_dm"
}
```

```python
await redis.publish("moddy:bot", json.dumps({
    "type": "module_updated",
    "guild_id": guild_id,
    "module_id": "welcome_dm",
}))
```

`bot.py::_handle_bot_event` reacts by unloading that guild's modules; the next
join re-reads from the DB. `config_updated`, `module_disabled` and
`logging_updated` have the same effect today, but send `module_updated` — the
others may diverge later.

Without this event the bot keeps sending the **old** DMs until it restarts.

## 8. Constants to mirror

From `modules/welcome_dm.py` — keep them in sync, the dashboard should enforce
the same caps client-side:

| Constant | Value |
|---|---|
| `MAX_WELCOME_DMS` | `3` |
| `MAX_MESSAGE_LENGTH` | `1500` |
| `DEFAULT_ACCENT_COLOR` | `0x5865F2` (5793266) |
| `CONFIG_VERSION` | `2` |
| id prefix | `wdm_` + 8 lowercase hex |

The sibling channel module uses the same names with `MAX_WELCOME_MESSAGES = 5`
and a `wm_` prefix — don't cross-wire them.

## 9. Implementation checklist

- [ ] Read `data #> '{modules,welcome_dm}'`, apply the v1 fallback of §5.
- [ ] Validate §4 before writing (count, unique ids, message length, colour range).
- [ ] Generate `wdm_` + 8 hex for new entries; never reuse an existing id.
- [ ] Write the **whole** object with `version: 2` (no partial merge).
- [ ] Fill `created_by` / `created_at` on new entries, preserve them on edits.
- [ ] Convert `#RRGGBB` ↔ `int` at the UI boundary; `null` = default colour.
- [ ] Publish `module_updated` on `moddy:bot` after every write.
- [ ] Module on/off in the UI = the entries' `enabled` flags, not a root key.
- [ ] Preview substitutes placeholders literally, unknown tokens untouched.
